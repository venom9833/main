## 1. 목적 및 배경 (Purpose)

LinkDrop V2의 `/series/` 파이프라인은 다음 구조적 문제를 안고 있다:

- 브라우저 저장소 3종 혼용 (IndexedDB 3개 + sessionStorage 12개 + localStorage 중복)
- 타입/인터페이스 page.tsx마다 개별 선언 (공유 타입 파일 없음)
- 각 page.tsx 700~1500줄 모놀리스 (상태·API·UI·IDB 혼재)
- 사용자가 5개 페이지를 수동으로 이동해야 함

**LinkDropV3는 `/series/` 파이프라인만을 위한 독립 프로젝트로 처음부터 올바르게 설계한다.**

### 핵심 목표

> **사용자가 소스 파일만 업로드하면, AI 에이전트가 대본 → 영상 생산 → YouTube 업로드 → 채널 관리를 자동 완주한다.**
> **1일 1챕터 생성, 사용자가 종결 시점을 결정한다.**

### ★ 1화 집중 원칙 (최우선)

> **모든 역량은 챕터 1에 집중한다.**
> 1화가 네이버·유튜브에 최초 공개되고, 시청자는 1화만 보고 시리즈 구독 여부를 결정한다.
> 2화 이후는 1화 성공 이후에만 의미가 있다.

| 항목 | ch01 | ch02 이후 |
|------|------|----------|
| 씬(Scene) 수 | 6~8개 | 5~8개 |
| 씬당 컷(Cut) 수 | 3~5개 | 3~5개 |
| 챕터 총 컷 수 | 20~30개 | 20~30개 |
| 챕터 총 텍스트 | 2,500~4,000자 | 2,500~4,000자 |
| 프롬프트 | 1화 전용 강화 지침 포함 | 일반 지침 |
| 마지막 씬 마지막 컷 | "다음화가 궁금한" 열린 훅 필수 | 동일 |
| 연재 결정 | 시청자 반응으로 결정 | 반응 확인 후 진행 |

### 자동화 단계 전략 (핵심 로드맵)

> **현재는 사용자 개입 게이트를 최대로 열어 품질을 검증한다.**
> **결과물 품질이 표준화되는 시점마다 게이트를 하나씩 닫아 AI 완전 자율 제작 공정으로 수렴한다.**

| 단계 | 개입 게이트 수 | 설명 |
|------|-------------|------|
| Phase A (현재) | 5개 | 소스 업로드 / 세계관 / 대본 / 키프레임 / 업로드 — 모두 사용자 확인 |
| Phase B | 3개 | 세계관·키프레임 autoApprove ON — 품질 기준 충족 확인 후 |
| Phase C | 1개 | 대본 autoApprove ON — 소스 업로드만 남음 |
| Phase D (목표) | 0개 | 소스 업로드조차 스케줄러 자동화 — 완전 Zero-Hands |

**구현 메커니즘**: `v3_series.settings` JSON의 `autoApprove*` 플래그로 게이트별 독립 제어
```json
{
  "autoApproveSource":   false,
  "autoApproveWorld":    false,
  "autoApproveScript":   false,
  "autoApproveKeyframe": false,
  "autoApproveUpload":   false
}
```
플래그를 `true`로 바꾸면 해당 게이트를 건너뛰고 자동 진행. 코드 수정 없이 시리즈별 개별 설정 가능.

## 2. 전략적 결정 (Strategic Decisions)

| 항목 | 결정 | 이유 |
|------|------|------|
| Supabase | V2와 **공유** | 캐릭터 데이터 재활용, 별도 인프라 불필요 |
| V2 이전 트리거 | **Zero-Hands 자동화 완성** 시 | 소스 업로드 1번 → 전자동 완주 상태 |
| V2 통합 방식 | **V3 독립 API, V2 프론트엔드가 호출** | 사용자 UX 분산 방지, 코드 분리 유지 |
| 시리즈 길이 | **무제한** — 사용자가 명시적으로 종결 결정 | 소비자 반응 보고 継속/중단 결정 |
| 챕터 생산 | **1일 1챕터** — `run_script()` 1회 호출 = 1챕터만 생성 | 유튜브 1일 1업로드 목표 |
| 게재 플랫폼 | **YouTube MP4 + 네이버 웹소설** 이중 게재 | 영상+텍스트 플랫폼 동시 공략 |
| TREND 단계 | **제거** — 소스 파일 업로드로 대체 | 사용자가 직접 팩트 소재 제공 |

### V2 이전 완료 기준 (3가지)
1. 소스 파일 업로드만으로 MP4 생성 성공률 90% 이상
2. YouTube 업로드 자동화 동작 확인
3. 사용자 승인 포인트 3개 이하 유지

## 4. 데이터 저장소 설계 (Storage Design)

### 4-A. 브라우저: IDB 1개로 통합

| 항목 | 값 |
|------|-----|
| DB명 | `linkdrop_v3` |
| 버전 | `1` |

| Store명 | keyPath | 용도 |
|---------|---------|------|
| `series` | `id` | 시리즈 메타 (세계관, 설정, 상태) |
| `chapters` | `[seriesId, chapter]` | 챕터별 대본 + 메타 |
| `scenes` | `[seriesId, chapter, sceneIndex]` | 씬별 키프레임 + 서브씬 |
| `draft` | `key` | 편집 중 임시 저장 (V2 sessionStorage 대체) |

**draft 키 체계**: `draft:world:{seriesId}`, `draft:script:{seriesId}:{chapter}`

### 4-B. seriesStore.ts — 유일한 저장소 진입점

```typescript
interface SeriesStore {
  // 시리즈 CRUD
  create(topic: string, settings?: Partial<SeriesSettings>): Promise<Series>;
  get(seriesId: string): Promise<Series | null>;
  list(filter?: { status?: string }): Promise<Series[]>;
  update(seriesId: string, patch: Partial<Series>): Promise<void>;

  // 챕터
  getChapter(seriesId: string, chapter: number): Promise<Chapter | null>;
  saveChapter(seriesId: string, chapter: number, data: ChapterDraft): Promise<void>;
  approveChapter(seriesId: string, chapter: number): Promise<void>;

  // 씬
  getScenes(seriesId: string, chapter: number): Promise<Scene[]>;
  updateScene(seriesId: string, chapter: number, sceneIndex: number, patch: Partial<Scene>): Promise<void>;

  // 드래프트
  saveDraft(key: string, data: unknown): Promise<void>;
  loadDraft<T>(key: string): Promise<T | null>;

  // 동기화 (IDB ↔ Supabase)
  syncToServer(seriesId: string): Promise<void>;
  syncFromServer(seriesId: string): Promise<void>;
}
```

**규칙**: `seriesStore.ts` 외부에서 `indexedDB.open()` 직접 호출 절대 금지.

### 4-C. Supabase 테이블 (v3_ prefix, V2 충돌 방지)

```sql
v3_series          -- 시리즈 마스터 (status, world_data, pipeline_step, series_code, current_chapter)
v3_chapters        -- 챕터별 대본 JSON (chapter_number, scenes JSON, approved 플래그)
v3_chapter_meta    -- 챕터별 메타 (복선 목록, 결말 한줄 요약)
v3_scenes          -- 씬별 keyframe_url, tts_url, clip_url, status
v3_pipeline_runs   -- 실행 로그 (에이전트 추적, 재시작 복구용)
v3_youtube_uploads -- YouTube 업로드 기록 + video_id
v3_wiki_chunks     -- RAG 임베딩 청크 (pgvector 768차원)
v3_wiki_pages      -- wiki 4개 핵심 페이지 (world/characters/foreshadows/timeline)
```

**V2 공유 테이블**: 없음 (모두 독립)

> ✅ `characters`: V2 Supabase 테이블 대신 **로컬 `data/characters/` JSON 파일** 사용 — `casting_service.py`가 직접 읽음
> ✅ `series_trends`: TREND 단계 폐기, 소스 업로드로 대체 — 참조 제거

**동기화 원칙**: Supabase = 단일 진실 공급원(Single Source of Truth). IDB = 빠른 읽기 캐시.

### 4-D. 씬(Scene) / 컷(Cut) 계층 구조

**씬(Scene)**: 영상 제작 기준 — 동일 장소·시각·등장 캐릭터가 유지되는 블록
**컷(Cut)**: 씬의 요소를 이어받은 세부 묘사 + 키프레임 이미지 단위 (TTS 1개 포함)

| 단위 | `scene_index` | `cut_index` | 데이터 |
|------|:---:|:---:|------|
| 씬 | 1~N | — | `location` / `time_of_day` / `characters` / `atmosphere` / `scene_hint` |
| 컷 | 씬 번호 | 씬 내 1~M | `text` / `type`(narration\|dialogue\|mixed) / `speaker`(캐릭터명 or null) / `tts_voice`(edge-tts 음성명) / `image_focus` / `image_prompt` / `is_hook` |
| HOOK 복사본 | 0 | 1 | **HOOK 컷** 자체를 맨 앞으로 복사 (영상 도입부) |

**씬 전환 기준**: 장소 이동, 시간 이동, 등장 캐릭터 구성 변경 — 이 중 하나라도 바뀌면 새 씬
**컷 전환 기준**: 씬 설정을 유지한 채, 카메라 포커스·나레이션 호흡·감정 강도가 달라지는 단위

**dialogue 컷 상한 (★ 제작 공수 직결)**:

> dialogue 컷 = 립싱크 영상 구간 = 제작 공수 1컷당 증가. 최소화가 원칙.

| 챕터 | dialogue 컷 상한 | 초과 처리 |
|------|:---:|----------|
| ch01 | **3개** | 초과 대사 → 간접 인용 narration 재작성 |
| ch02~ | **5개** | 동일 |

**2-Pass 씬/컷 구조화**:
- **Pass 1** (`_build_structure_prompt`): 대본 원문 그대로 씬/컷 분할. 규칙 9개 (모순 없음)
- **Pass 2** (`_absorb_dialogue_cuts`): 상한 초과 dialogue 컷만 추출 → 단일 Gemini 배치 호출로 간접 인용 narration 재작성
  - 보존 우선순위: `is_hook` 컷 > 앞 순서
  - 변환 예: `"하하, 별것 아닙니다."` → `"그는 웃어 넘겼지만 손이 떨렸다."`
- 4곳 적용: `generate_chapter` / `regenerate_chapter` / `revise_chapter_content` / `restructure_scenes`

**컷 타입 수동 수정**: UI `narr`/`대사` 라벨 클릭 → `PATCH /api/v1/series/{id}/scenes/{scene_code}` 즉시 반영

**씬 힌트(`scene_hint`) — 컷 계승 원칙**:
- 씬 정의 시 핵심 시각 키워드를 `scene_hint`로 명시 (15자 이내, 예: "새벽 형광등, 차가운 블루 톤")
- 이 씬에 속한 **모든 컷의 `image_prompt`는 반드시 `scene_hint`로 시작**
- 컷 `image_prompt` = `scene_hint`(영문) + `image_focus`(컷별 포커스 영문)
- 이를 통해 씬 내 모든 키프레임이 동일한 시각 DNA를 공유 → 영상 일관성 보장

**씬 공통 맥락(`scene_meta`)**: `location/time_of_day/characters/atmosphere/scene_hint` — DB `scene_meta` JSONB 컬럼에 저장
**챕터 총 컷 수**: 20~30개 (씬 6개 × 컷 4개 = 24개 기준)

### 4-E. 시리즈 식별자 체계 (마스터코드)

| 컬럼 | 값 | 설정 시점 |
|------|----|---------:|
| `id` | UUID (PK) | 시리즈 생성 즉시 |
| `series_code` | `YYYYMMDD_HHMMSS_ch01s{씬번호:02d}{h\|n}c{컷번호:02d}` | ch01 대본 생성 완료 후 |

**series_code 예시**: `20260410_143022_ch01s05hc01`
- 의미: 2026-04-10 14:30:22에 ch01 생성, HOOK은 5번째 씬의 1번째 컷

**컷 코드 규칙**: `{series_code}_ch{챕터:02d}s{씬인덱스:02d}{h|n}c{컷인덱스:02d}`
- 예: `20260410_143022_ch01s05hc01_ch01s00nc01` (ch01 HOOK 도입부 복사본)
- 예: `20260410_143022_ch01s05hc01_ch02s03nc02` (ch02 3번째 씬 2번째 컷)

**HOOK 컷 규칙** ★ (씬 단위 아닌 컷 단위):
- `is_hook`은 **씬이 아닌 컷에 부여** — 대본 전체에서 감정 충격이 가장 강렬한 단 1개 컷
- 첫 씬 첫 컷 금지 (도입 설정 컷은 HOOK이 될 수 없음)
- `_parse_scenes_json()`: HOOK 컷(`is_hook=True`)을 `scene_index=0, cut_index=1`로 복사 후 result 맨 앞에 삽입
- **방어 로직**: Gemini가 `is_hook=True`를 여러 컷에 부여한 경우 → 마지막 후보 1개만 선택, 나머지는 `False`로 리셋
- 폴백: `is_hook=True` 컷이 없으면 마지막 씬의 마지막 컷을 HOOK으로 자동 지정

### 4-F. 컷별 제작 품질 전략 (render_type)

> **ch01은 영화급으로 최대 공들인다. ch02부터는 HOOK 씬만 영화급, 나머지는 경량 제작.**

| 챕터 | 씬 종류 | `render_type` | 제작 방식 |
|------|---------|:---:|----------|
| ch01 | 전체 모든 씬/컷 | `ai_video` | 영화급 AI 영상 |
| ch02+ | HOOK 씬 컷 | `ai_video` | 영화급 AI 영상 |
| ch02+ | 나머지 씬 컷 | `keyframe_anim` | 키프레임 이미지 + Remotion 정지 애니메이션 |

**`ai_video` 제작 방식 — 단계별 전환**

| 단계 | 방식 | 설명 |
|------|------|------|
| **현재 (Phase A)** | 사용자 수동 제작 | 품질 기준 확보 전 — 사용자가 Kling/Runway 등으로 직접 제작 후 업로드 |
| **미래 (Phase B)** | ComfyUI Cloud 자동화 | 정교한 워크플로우 자동 실행 — `render_service.py`가 ComfyUI API 호출 |

**현재 `ai_video` 컷 파이프라인**:
1. `render_service.py`가 `render_type = "ai_video"` 컷 감지
2. 해당 컷의 `image_prompt`, `text`, `scene_meta`를 사용자에게 제공
3. 사용자가 외부 도구로 MP4 제작 → 수동 업로드
4. 업로드된 MP4를 R2에 저장, `clip_url` 갱신 후 파이프라인 재개

**미래 ComfyUI Cloud 연동 (구현 예정)**:
- ComfyUI 워크플로우 JSON + `scene_hint` + `image_prompt` → 고품질 영상 자동 생성
- `render_service.py`의 `ai_video` 분기에서 ComfyUI API 호출로 교체
- 데이터 구조(`render_type`, `scene_meta`, `image_prompt`)는 이미 준비 완료

**근거**:
- ch01은 시리즈 첫 공개 — 시청자가 구독 여부를 결정하는 유일한 판단 기준
- ch02+는 HOOK으로 시청자를 잡고, 본편은 경량 제작으로 생산 비용·시간 절감

## 5. 에이전트 파이프라인 (Agent Pipeline)

### 5-A. 1일 1챕터 정책 (핵심 설계 원칙)

> **`run_script()`는 1회 호출 시 `current_chapter` 1개만 생성한다. 절대 다중 챕터 생성 금지.**

- `v3_series.current_chapter` 컬럼으로 현재 생산 중인 챕터 번호 추적
- 챕터 완료(`CHAPTER_DONE`) 시: `current_chapter += 1`, 파이프라인 정지
- 다음 챕터는 사용자가 "N+1화 시작" 버튼을 눌러야만 재개
- 종결은 사용자가 "시리즈 종결" 버튼으로 명시적 결정 → DONE

### 5-B. 자동/수동 구분

| 단계 | 방식 | AI 호출 | 설명 |
|------|------|---------|------|
| `source_upload` | **게이트** | 없음 | 소스 파일(.txt/.srt/.pdf) 업로드 + wiki RAG 인제스트 |
| `world` | 자동 | Gemini 1회 | RAG 소스 컨텍스트 + 캐릭터 → 세계관 자동 생성 |
| `casting` | 자동 | 없음 | V2 characters DB → 자동 캐스팅 |
| `script` | **반자동** | Gemini **3회** | STEP1 순수 대본 생성 + STEP2 씬/컷 JSON 구조화(Pass1) + STEP3 대사 흡수(Pass2) → 사용자 **승인 대기** |
| `keyframe_setup` | **게이트** | 없음 | 키프레임 생성 방식 선택 (Gemini/Pillow) |
| `keyframe` | 자동 | 조건부 | art_styles.json 기반 (Pillow) or Gemini 이미지 생성 |
| `tts` | 자동 | 없음 | edge-tts 씬별 병렬 생성 |
| `render` | 자동 | 없음 | Remotion + FFmpeg 씬별 병렬 합성 |
| `upload` | **반자동** | 없음 | 최종 MP4 확인 후 사용자 **업로드 승인** |
| `youtube_manage` | 자동 | 없음 | 썸네일·설명·태그·공개 예약 자동 처리 |
| `naver_upload` | 자동 | 없음 | 네이버 웹소설 텍스트 업로드 (stub, 실구현 예정) |
| `chapter_done` | **게이트** | 없음 | 사용자 결정: "N+1화 시작" or "시리즈 종결" |

**AI 호출 총계**: 챕터당 최대 3회 (world 1회 — ch1만, script Pass1 1회, script Pass2 대사흡수 1회)
**나머지 단계**: 100% 로컬/DB 처리 — AI 최소화 원칙 준수

### 5-C. 상태 머신

```
[IDLE]
  → (trigger)  → [AWAITING_SOURCE_UPLOAD]  ← 소스 파일 업로드 게이트 #0
  → (approve)  → [WORLD]
  → (auto)     → [CASTING]
  → (auto)     → [SCRIPT]  ← current_chapter 1개만 생성
  → (wait)     → [AWAITING_SCRIPT_APPROVAL]  ← 사용자 승인 #1
  → (approve)  → [AWAITING_KEYFRAME_SETUP]  ← 키프레임 방식 선택 게이트 #2
  → (approve)  → [KEYFRAME] → [TTS] → [RENDER]
  → (wait)     → [AWAITING_UPLOAD_APPROVAL]  ← 사용자 승인 #3
  → (approve)  → [UPLOAD] → [YOUTUBE_MANAGE] → [CHAPTER_DONE]

  [CHAPTER_DONE] ← current_chapter += 1, 파이프라인 정지
    → (사용자: N+1화 시작) → [SCRIPT]  ← 다음 챕터 생성 (2화부터 AWAITING_KEYFRAME_SETUP 없이)
    → (사용자: 시리즈 종결) → [DONE]

  어느 단계든 실패 시 → [FAILED]
  사용자 재시도 → 해당 단계부터 재개 (성공 단계 보존)
```

**승인 포인트**: 최대 4개 (source_upload / script / keyframe_setup / upload)
**2화 이후**: AWAITING_SOURCE_UPLOAD + AWAITING_KEYFRAME_SETUP 스킵, SCRIPT → AWAITING_SCRIPT_APPROVAL부터 재개

**AWAITING_SCRIPT_APPROVAL 단계 UI 기능**:
| 버튼 | API | 설명 |
|------|-----|------|
| 대본 교정 | `POST /revise-script` | 스토리 유지, 규칙 위반(대사 30%·15자 미만)만 수정. 완료 감지 폴링(1.5초×80회) |
| 대본 재생성 | `POST /chapters/{ch}/regenerate` | 완전 새 대본 생성 |
| ↓ JSON | `GET /chapters/{ch}/scenes` 집계 | 최신 씬/컷 데이터 다운로드 (교정/재생성 중 비활성화) |
| 컷 타입 토글 | `PATCH /scenes/{scene_code}` | narr↔대사 즉시 전환 |
| 컷 예상 시간 | 클라이언트 계산 | `text.length ÷ 5`초 뱃지 표시 (씬합계·챕터합계 포함) |

### 5-D. APPROVAL_TRANSITIONS (FastAPI 라우터 `/approve/{step}` 기준)

| approve key | 다음 상태 |
|-------------|----------|
| `source_upload` | `WORLD` |
| `world` | `CASTING` |
| `script` | `AWAITING_KEYFRAME_SETUP` |
| `keyframe_setup` | `KEYFRAME` |
| `upload` | `UPLOAD` |

### 5-E. AUTO_TRANSITIONS (자동 전이)

| 현재 상태 | 다음 상태 |
|----------|----------|
| `WORLD` | `CASTING` |
| `CASTING` | `SCRIPT` |
| `KEYFRAME` | `TTS` |
| `TTS` | `RENDER` |
| `RENDER` | `AWAITING_UPLOAD_APPROVAL` |
| `UPLOAD` | `YOUTUBE_MANAGE` |
| `YOUTUBE_MANAGE` | `CHAPTER_DONE` |

### 5-F. 재시도 전략

| 단계 | 최대 재시도 | 재시도 단위 |
|------|-----------|-----------|
| world | 3 (지수 백오프: 3→6→12초) | 전체 재생성 |
| script | 3 (챕터별) | 실패 챕터만 재생성, 성공 챕터 보존 |
| tts | 3 (씬별) | 실패 씬만 재생성 |
| render | 2 (씬별) | 실패 씬만 재렌더 |
| upload | 2 (30초 간격) | YouTube API 쿼터 대기 후 재시도 |

**클립별 재시도 원칙**: 실패한 씬/챕터만 선택 재생성. 전체 파이프라인 재시작 없음.

## 6. 소스 업로드 & RAG Wiki 시스템 (Knowledge Engine)

### 6-A. 소스 파일 업로드 (TREND 대체)

사용자가 직접 팩트/각색 소재를 업로드한다.

| 항목 | 내용 |
|------|------|
| 지원 형식 | `.txt` (소설·시나리오·메모), `.srt` / `.vtt` (자막), `.pdf` (기사·보고서) |
| 업로드 API | `POST /wiki/{id}/sources/upload-file` (multipart/form-data) |
| 저장 위치 | Supabase `v3_wiki_chunks` (RAG 인제스트) |
| 활용 시점 | `world_service.py`: RAG top-K 검색 → Gemini world 생성 프롬프트 주입 |

**소스 없이 진행 가능**: 업로드 없이 "바로 진행" → topic 기반 세계관 생성

### 6-B. V2 대비 V3의 RAG 차이

| 항목 | V2 (현재) | V3 (목표) |
|------|-----------|-----------|
| 저장소 | 로컬 파일 (`wiki/{id}/*.md`) | Supabase pgvector |
| 페이지 선택 | Gemini가 STEP 1에서 수동 판단 | 자동 벡터 검색 (top-K) |
| 인제스트 | API 수동 호출 필요 | 파이프라인 단계별 자동 트리거 |
| 위키 구조 | 7~10개 MD 파일 (world, foreshadows, timeline 등) | 4개 핵심 페이지 + 청크 벡터 DB |
| 로컬 의존 | 서버 파일시스템 필수 | Supabase 완전 의존 (서버리스 가능) |
| 소스 주입 | 없음 (트랜드 DB에서 자동) | ★ 사용자 업로드 파일 RAG 직접 주입 |

### 6-C. Supabase pgvector 테이블

```sql
-- pgvector 확장 활성화 (Supabase에서 기본 지원)
create extension if not exists vector;

-- RAG 청크 저장소
create table v3_wiki_chunks (
  id           uuid primary key default gen_random_uuid(),
  series_id    uuid not null references v3_series(id) on delete cascade,
  source_type  text not null,
    -- 'world' | 'source_file' | 'character' | 'chapter' | 'foreshadow' | 'user_note'
  source_ref   text,           -- 참조 (예: 'chapter:3', 'character:서지안', 'file:천한여종.txt')
  content      text not null,  -- 원본 텍스트 청크
  embedding    vector(768),    -- gemini-embedding-001 (768차원)
  metadata     jsonb,          -- { chapter, charId, keyword, ... }
  created_at   timestamptz not null default now()
);

-- 검색 성능 인덱스 (HNSW)
create index v3_wiki_chunks_embedding_idx
  on v3_wiki_chunks
  using hnsw (embedding vector_cosine_ops)
  with (m = 16, ef_construction = 64);

create index v3_wiki_chunks_series_idx on v3_wiki_chunks(series_id, source_type);

-- 간편 wiki 4개 핵심 페이지 (자동 생성·갱신)
create table v3_wiki_pages (
  id          uuid primary key default gen_random_uuid(),
  series_id   uuid not null references v3_series(id) on delete cascade,
  slug        text not null,       -- 'world' | 'characters' | 'foreshadows' | 'timeline'
  content_md  text not null default '',
  updated_at  timestamptz not null default now(),
  unique(series_id, slug)
);
```

### 6-D. 자동 인제스트 타이밍

파이프라인 단계가 완료될 때 자동으로 RAG DB에 반영한다. 별도 API 호출 불필요.

| 파이프라인 단계 완료 | 자동 인제스트 내용 | source_type |
|-------------------|--------------------|-------------|
| 소스 파일 업로드 완료 | 업로드 파일 텍스트 → 청크 분할 | `source_file` |
| `world` 생성 완료 | 세계관 전체 텍스트 → 청크 분할 | `world` |
| 캐릭터 배정 완료 | 캐릭터별 프로필 + 상황 + 감정선 | `character` |
| 챕터 **승인** 완료 | 챕터 대본 텍스트 → 씬 단위 청크 | `chapter` |
| 복선 감지 시 | 자동 추출된 복선 항목 | `foreshadow` |

**청크 분할 전략**: 300~500자 단위, 씬 경계(`---`) 우선 분할. 오버랩 50자.

### 6-F. 간편 Wiki 4개 핵심 페이지

V2의 7~10개 파일 구조를 4개로 통합. 파이프라인이 진행될수록 자동 갱신된다.

| slug | 내용 | 자동 갱신 시점 |
|------|------|--------------|
| `world` | 장르, 문체, 갈등 구조, 배경, 핵심 관계 | `world` 단계 완료 시 |
| `characters` | 등장인물 전원 프로필 + 현재 심리 상태 (arc) | 챕터 승인마다 갱신 |
| `foreshadows` | 심어진 복선 목록 + 회수 여부 | 챕터 승인마다 Gemini 추출 |
| `timeline` | 챕터별 사건 요약 + 시간순 흐름 | 챕터 승인마다 자동 추가 |

**갱신 규칙**:
- `world`, `characters` — 전체 재작성 (최신 상태 유지)
- `foreshadows` — 누적 추가 (회수된 복선은 `[회수됨]` 표기)
- `timeline` — 챕터 승인마다 1줄 추가 (append only)

## 7. UI 설계 원칙 (UI Design)

### 페이지: 8개 → 3개

| V3 페이지 | 역할 | V2 대체 |
|-----------|------|---------|
| `/` | 시리즈 목록 + 상태 카드 그리드 | 신규 |
| `/create` | 소스 파일 드래그앤드롭 업로드 | trend + world 통합 |
| `/series/[id]` | 파이프라인 진행 + 승인 + 챕터 제어 | script + keyframe + wiki 통합 |

### 소스 업로드 화면 (`/create`)

- 드래그앤드롭 파일 업로드 영역 (`.txt` / `.srt` / `.pdf`)
- 첫 번째 파일명에서 주제 자동 추출 (수정 가능)
- `시리즈 시작` 버튼 1개
- 흐름: createSeries → 파일 병렬 업로드 → approve/source_upload → `/series/{id}` 이동

### 상세 페이지 (`/series/[id]`)

- **상단**: 파이프라인 스테퍼 (source → world → casting → script → keyframe → tts → render → upload → done)
- **중앙**: 현재 단계 콘텐츠
  - `AWAITING_SOURCE_UPLOAD`: SourceUploadEditor (추가 업로드 허용)
  - `AWAITING_WORLD_APPROVAL`: WorldEditor (세계관 확인/편집)
  - `AWAITING_SCRIPT_APPROVAL`: 챕터 대본 카드 + JSON 다운로드 + `승인` 버튼
  - `AWAITING_KEYFRAME_SETUP`: KeyframeSetupEditor (Gemini/Pillow 선택)
  - `AWAITING_UPLOAD_APPROVAL`: 최종 MP4 미리보기 + `YouTube 업로드` 버튼
  - `CHAPTER_DONE`: ChapterDonePanel ("N+1화 시작" / "시리즈 종결")
- **하단**: 실행 로그 타임라인
- **에러 시**: 실패 단계 빨간 표시 + `재시도` 버튼 (해당 단계만)

### 대본 승인 패널 (AWAITING_SCRIPT_APPROVAL)

- 현재 `current_chapter`의 씬 목록 표시
- scene_index=0 씬: "훅 도입 (amber)" 강조 표시
- 씬별: 씬코드 + 대사 텍스트 + is_hook 여부
- 하단: `{series_code}_ch{chapter:02d}_script.json` 다운로드 버튼
- 승인 버튼 → AWAITING_KEYFRAME_SETUP 진입

### 챕터 완료 패널 (CHAPTER_DONE)

- "N화 완료" 안내
- "N+1화 시작" 버튼 → `POST /series/{id}/next-chapter`
- "시리즈 종결" 버튼 → 2단계 확인 → `POST /series/{id}/terminate`

### 진행 상태 모니터링

- SSE 이벤트 버스로 실시간 상태 수신 (`GET /series/{id}/events`)
- 5초 폴링 폴백 (`GET /api/v1/series/{id}/status`)
- 단계 변경 시 토스트 알림: *"챕터 1 대본 생성 완료"*, *"씬 5 TTS 실패 — 재시도 중"*

## 8. API Contract (V2 ↔ V3 연동)

### V3 REST API 엔드포인트 (Base: `http://localhost:8100/api/v1`)

```
# 시리즈
POST   /series                         신규 시리즈 생성 (AWAITING_SOURCE_UPLOAD 상태로 생성)
GET    /series                         목록 조회
GET    /series/{id}                    상세 + 파이프라인 상태
PATCH  /series/{id}                    설정 수정

# 파이프라인 제어
POST   /series/{id}/run                시작/재개
POST   /series/{id}/retry/{step}       특정 단계 재시도
POST   /series/{id}/approve/{step}     단계 승인 (source_upload/world/script/keyframe_setup/upload)
GET    /series/{id}/status             현재 상태 (폴링용)
GET    /series/{id}/events             SSE 이벤트 스트림 (실시간 상태)

# 챕터 제어 (1일 1챕터 정책)
POST   /series/{id}/next-chapter       CHAPTER_DONE → SCRIPT (다음 챕터 시작)
POST   /series/{id}/terminate          CHAPTER_DONE → DONE (시리즈 종결)
GET    /series/{id}/chapters/{ch}      챕터 대본 조회
GET    /series/{id}/chapters           전체 챕터 목록

# 씬
GET    /series/{id}/chapters/{ch}/scenes
POST   /series/{id}/chapters/{ch}/scenes/{idx}/retry

# Wiki (소스 업로드 + RAG)
POST   /wiki/{id}/sources/upload-file  소스 파일 업로드 (multipart)
GET    /wiki/{id}/pages                wiki 4개 페이지 목록
GET    /wiki/{id}/pages/{slug}         페이지 내용 (world/characters/foreshadows/timeline)
PUT    /wiki/{id}/pages/{slug}         페이지 수동 편집
POST   /wiki/{id}/search               RAG 검색 (query → 관련 청크 반환)

# YouTube
POST   /series/{id}/youtube/upload
GET    /series/{id}/youtube/status
PATCH  /series/{id}/youtube/metadata
```

### V2 연동 방식

V2 프론트엔드에 `SeriesDashboard` 컴포넌트 1개 추가 → V3 API를 직접 fetch.
사용자는 V2 UI 안에서 시리즈 파이프라인 전체를 조작. 별도 앱 이동 없음.

**인증**: V2/V3 동일 Supabase 프로젝트 → Supabase Auth JWT 토큰 공유.

## 9. 기술 스택 결정 (Tech Stack)

| 항목 | 선택 | 이유 |
|------|------|------|
| 에이전트 오케스트레이터 | FastAPI BackgroundTasks + `v3_pipeline_runs` DB 영속화 | 별도 인프라 없음. 재시작 시 DB에서 복구. 확장 시 Celery+Redis 교체 가능 |
| TTS | edge-tts (1순위) + Supertone 폴백 | 무료 우선, 안정성 보강 |
| 영상 렌더 | Remotion + FFmpeg | V2 검증 완료 스택 유지 |
| YouTube | Google Data API v3 (Resumable Upload) | 대용량 MP4 대응 |
| 이미지 저장 | Cloudflare R2 (V2와 동일 버킷) | 로컬 저장 절대 금지 |
| 동시 렌더 제한 | `MAX_CONCURRENT_RENDERS=3` (환경변수) | CPU/메모리 과부하 방지 |
| 실시간 상태 | SSE (Server-Sent Events) event_bus | 폴링보다 낮은 레이턴시 |
