### 씬(Scene) / 컷(Cut) 계층 구조

**씬(Scene)**: 영상 제작 기준 — 동일 장소·시각·등장 캐릭터가 유지되는 블록
**컷(Cut)**: 씬의 요소를 이어받은 세부 묘사 + 키프레임 이미지 단위 (TTS 1개 포함)

| 단위 | `scene_index` | `cut_index` | 데이터 |
|------|:---:|:---:|------|
| 씬 | 1~N | — | `location` / `time_of_day` / `characters` / `atmosphere` / `scene_hint` |
| 컷 | 씬 번호 | 씬 내 1~M | `text` / `type`(narration\|dialogue\|mixed) / `speaker`(캐릭터명 or null) / `tts_voice`(edge-tts 음성명) / `image_focus` / `image_prompt` / `is_hook` |
| HOOK 복사본 | 0 | 1 | **HOOK 컷** 자체를 맨 앞으로 복사 (영상 도입부) |

### ★ 씬/컷 2단계 분할 원칙 (필수)

대본을 씬·컷으로 분해할 때 반드시 아래 순서를 지킨다.

#### 1단계 — 씬 분할 (큰 단위, 먼저 확정)

> 대본 전체를 먼저 읽고, **공간·시간·등장인물·문맥 흐름** 기준으로 씬 경계를 나눈다.

씬이 바뀌는 기준 — 아래 중 **하나라도** 바뀌면 새 씬:

| 기준 | 예시 |
|------|------|
| 공간(장소) 변경 | 카페 → 사무실 로비, 실내 → 실외 |
| 시간 변경 | 오전 → 저녁, 당일 → 다음날 |
| 등장인물 구성 변경 | A+B 대화 → A 혼자, 또는 제3자 합류 |
| 문맥의 큰 흐름 전환 | 갈등 고조 국면 → 화해 시도, 긴장 → 이완 |

> ⚠️ **씬은 촬영 단위다.** 같은 장소라도 시간이 바뀌면 별개 씬이다.  
> ⚠️ 문맥 흐름은 보조 기준이다 — 공간·시간·인물이 유지되면 분위기만 달라져도 같은 씬.

#### 2단계 — 컷 분할 (씬 확정 후, 씬 내부를 세분화)

> 1단계에서 확정된 **각 씬 안에서만** 컷을 나눈다.  
> 씬 경계를 넘는 컷은 존재할 수 없다.

컷이 바뀌는 기준 — 씬 설정(장소·시간·인물)은 그대로 유지한 채:

| 기준 | 예시 |
|------|------|
| 카메라 포커스 변경 | 전체 공간 풀샷 → 손 클로즈업 |
| 나레이션·대화 호흡 단위 | 문장/대사 1~2개 단위로 자연스럽게 끊기는 지점 |
| 감정 강도 변화 | 정적 → 폭발, 냉소 → 눈물 |

> 씬당 컷 수: **3~5개** 유지 (2개 이하는 씬 자체가 너무 짧은 것, 6개 이상은 씬 분할 재검토)

#### 분할 절차 요약

```
대본 전체 독해
    ↓
[1단계] 공간 / 시간 / 등장인물 / 문맥 흐름 → 씬 경계 확정 (6~8개)
    ↓
[2단계] 각 씬 내부 → 카메라 앵글 / 호흡 / 감정 기준 → 컷 분할 (씬당 3~5개)
    ↓
전체 컷 수 합산: 20~30개 범위 확인
```

---

**씬 전환 기준**: 공간·시간·등장인물 구성·문맥 큰 흐름 — 이 중 하나라도 바뀌면 새 씬
**컷 전환 기준**: 씬 설정을 유지한 채, 카메라 포커스·나레이션 호흡·감정 강도가 달라지는 단위

**씬 힌트(`scene_hint`) — 컷 계승 원칙**:
- 씬 정의 시 핵심 시각 키워드를 `scene_hint`로 명시 (15자 이내, 예: "새벽 형광등, 차가운 블루 톤")
- 이 씬에 속한 **모든 컷의 `image_prompt`는 반드시 `scene_hint`로 시작**
- 컷 `image_prompt` = `scene_hint`(영문) + `image_focus`(컷별 포커스 영문)
- 이를 통해 씬 내 모든 키프레임이 동일한 시각 DNA를 공유 → 영상 일관성 보장

**씬 공통 맥락(`scene_meta`)**: `location/time_of_day/characters/atmosphere/scene_hint` — DB `scene_meta` JSONB 컬럼에 저장
**챕터 총 컷 수**: 20~30개 (씬 6개 × 컷 4개 = 24개 기준)

### 4-E. 시리즈 식별자 체계 (마스터코드)

| 컬럼 | 값 | 설정 시점 |
|------|----|---------:|
| `id` | UUID (PK) | 시리즈 생성 즉시 |
| `series_code` | `YYYYMMDD_HHMMSS_ch01s{씬번호:02d}{h\|n}c{컷번호:02d}` | ch01 대본 생성 완료 후 |

**series_code 예시**: `20260410_143022_ch01s05hc01`
- 의미: 2026-04-10 14:30:22에 ch01 생성, HOOK은 5번째 씬의 1번째 컷

**컷 코드 규칙**: `YYYYMMDD_HHMMSS_ch{챕터:02d}s{씬인덱스:02d}{h|n}c{컷인덱스:02d}`
- `series_code` 앞 두 파트(날짜`_`시간)를 timestamp prefix로 공유 → 전체 시리즈 컷이 동일 prefix를 가짐
- 예: `20260410_143022_ch01s05hc01` (ch01 5번째 씬 HOOK — 복사본·원본 **동일 코드**)
- 예: `20260410_143022_ch02s03nc02` (ch02 3번째 씬 2번째 컷)

> ⚠️ **HOOK 복사본의 scene_code는 `ch01s00hc01`이 아닌 원본과 동일한 코드를 사용한다.**
> `_persist_scenes_to_db`에서 `_orig_scene_index`/`_orig_cut_index`를 기준으로 생성하므로
> 복사본(`scene_index=0`)과 원본(`scene_index=N`)은 DB에서 다른 행이지만 scene_code는 같다.

**HOOK 컷 규칙** ★ (씬 단위 아닌 컷 단위):

#### HOOK 컷 선정
- `is_hook`은 **씬이 아닌 컷에 부여** — 대본 전체에서 감정 충격이 가장 강렬한 단 1개 컷
- 선정 기준: 시청자가 이 컷만 보고도 "계속 봐야겠다"는 충동을 느끼는 순간
  - 반전이 터지는 컷, 비밀이 폭로되는 컷, 가장 극적인 감정 폭발 컷
  - 첫 씬 첫 컷 금지 (도입 설정 컷은 HOOK이 될 수 없음)
- **방어 로직**: Gemini가 `is_hook=True`를 여러 컷에 부여할 경우 → **마지막 후보 1개만** 선택, 나머지는 `False`로 리셋
- 폴백: `is_hook=True` 컷이 하나도 없으면 마지막 씬의 마지막 컷을 자동 지정

#### 영상 재생 구조 — HOOK 컷은 영상에서 2회 등장

> HOOK 컷이 `ch01s03hc02` (3번째 씬, 2번째 컷)인 경우:

```
재생순서  scene_index  cut_index  scene_code       설명
───────────────────────────────────────────────────────────────
  [1]        0           1       ch01s03hc02    ← HOOK 복사본 (영상 맨 앞, 콜드오픈)
                                               ★ 원본과 동일 scene_code 사용
  [2]        1           1       ch01s01nc02    ← 씬1은 nc02부터 시작 (nc01 슬롯 의도적 공백)
  [3]        1           2       ch01s01nc03
   ...
  [N]        3           1       ch01s03hc01
  [N+1]      3           2       ch01s03hc02    ← HOOK 원본 (서사 흐름 속 자연스럽게 재등장)
                                               ★ 복사본과 동일 scene_code
  [N+2]      3           3       ch01s03hc03
   ...
  [끝]
```

> ★ **씬1 컷 번호 규칙**: `scene_index=1`의 컷은 `nc02`부터 시작 (`nc01` 슬롯은 의도적 공백)
> - 이유: HOOK 복사본이 nc01을 개념적으로 선점 → 씬1 첫 컷과의 혼동 방지
> - 씬2 이후: 정상적으로 `nc01`부터 시작

> ★ **HOOK 복사본과 원본의 scene_code 동일성**:
> - DB에서 복사본(`scene_index=0, cut_index=1`)과 원본(`scene_index=N, cut_index=M`)은 **다른 행**
> - 두 행의 `scene_code`는 **원본 위치 기준**으로 동일하게 생성됨 (`_orig_scene_index`/`_orig_cut_index` 사용)
> - 키프레임 생성 시 하나의 scene_code로 한 번만 렌더링 → 복사본·원본이 동일 이미지 공유
> - `local-scenes` API에서 중복 제거 **금지** — 두 위치 모두 반환해야 53번 설계 준수

- **복사본** (`scene_index=0`): 영상 도입부, 시청자를 붙잡는 역할
- **원본**: 서사 흐름 속 원위치 그대로 유지 — 시청자가 "아, 이게 그 장면이었구나" 체험
- 결과: HOOK 컷은 영상에서 **총 2회** 등장 (복사본 + 원본)

#### 구현
- Gemini 프롬프트: 씬 JSON에서 `is_hook` 제거 → 컷 JSON에 `is_hook` + `type` + `speaker` 추가
- `_parse_scenes_json(raw, chapter, world)`: HOOK 컷(`is_hook=True`) 방어 처리 후 `scene_index=0, cut_index=1`로 복사 → result 맨 앞에 삽입, 원본은 그대로 유지
- `_persist_scenes_to_db`: 복사본의 scene_code는 `_orig_scene_index`/`_orig_cut_index`(원본 위치) 기준 생성 → 복사본·원본 동일 코드
- `local-scenes` API (chapters.py): scene_code 중복 제거 **금지** — HOOK 2회 등장이 설계 의도
- `_build_speaker_voice_map(world)`: `world_data.charAVoice` 등을 읽어 캐릭터명 → edge-tts 음성명 매핑 생성 → 각 컷의 `tts_voice` 결정

### ★ 씬1 nc01 공백 + 4컷 그리드 그룹화 원칙 (🔒 LD-013)

#### nc01 의도적 공백 구현

`_parse_scenes_json()` 내 씬1 컷 인덱스 +1 오프셋:

```python
# script_service.py (절대 삭제 금지 — LD-013)
if scene_idx == 1:
    cut_idx += 1   # nc01 슬롯 공백: Gemini의 cut_index=1 → 저장은 cut_index=2(nc02)
```

- Gemini가 씬1에 `cut_index: 1` 을 출력해도 DB에는 `cut_index=2(nc02)`로 저장
- `(scene_index=1, cut_index=1)` 레코드가 DB에 존재하면 **버그** → 즉시 삭제

#### 4컷 그리드 그룹화 원칙

```
scenes 배열 구조:
  [0] HOOK 복사본 (scene_index=0)   ← 항상 맨 앞, 그룹화에서 제외
  [1] nc02 (scene_index=1, cut_index=2)
  [2] nc03
  [3] nc04
  [4] nc05
  [5] nc06
  ...

올바른 그룹 계산 (page.tsx):
  regularIdx = max(0, selectedIdx - 1)   ← HOOK(idx=0) 제외
  groupIndex  = floor(regularIdx / 4)
  groupStart  = groupIndex * 4 + 1       ← +1: HOOK 건너뜀

결과:
  selectedIdx=0(HOOK) → regularIdx=0, groupIndex=0, group=[nc02,nc03,nc04,nc05]
  selectedIdx=1(nc02) → regularIdx=0, groupIndex=0, group=[nc02,nc03,nc04,nc05] ✓
  selectedIdx=4(nc05) → regularIdx=3, groupIndex=0, group=[nc02,nc03,nc04,nc05] ✓
  selectedIdx=5(nc06) → regularIdx=4, groupIndex=1, group=[nc06,nc07,s02nc01,s02nc02] ✓
```

**절대 하지 말 것:**
- `Math.floor(selectedIdx / 4)` 방식 복원 (HOOK+nc02+nc03+nc04 혼합 그룹 발생)
- `cut_idx += 1` 오프셋 제거 (nc01이 DB에 생성되어 그룹 경계 오염)
- nc01 "없음"을 버그로 판단 → 코드/DB 수정 시도

### 4-E-2. 컷 type / speaker / tts_voice 필드

| 필드 | 타입 | 의미 |
|------|------|------|
| `type` | `"narration"` \| `"dialogue"` \| `"mixed"` | 나레이션 전용 / 대사 전용 / 혼합 |
| `speaker` | `string \| null` | `type=dialogue`일 때 캐릭터 이름 (narration이면 null) |
| `tts_voice` | `string` | edge-tts 음성명 (대사: 캐릭터 배정 성우, 나레이션: InJoon 고정) |

**성우 자동 배정 흐름**:
```
character JSON  voice_id: "dohyun"
      ↓
casting_service.py  world_data.charAVoice = "dohyun"
      ↓
_build_speaker_voice_map(world)  {"김태호": "ko-KR-GookMinNeural"}
      ↓
v3_scenes.tts_voice = "ko-KR-GookMinNeural"  (대본 생성 시 1회 저장)
      ↓
tts_service.py  scene["tts_voice"] 컬럼 직접 사용
```

- `type=narration` → `tts_voice = ko-KR-InJoonNeural` (중성 나레이터 고정)
- `type=dialogue` → speaker 이름으로 `world_data` 조회 → character JSON `voice_id` → VOICE_MAP 해석
- `type=mixed` → speaker 있으면 캐릭터 성우, 없으면 나레이터

### 4-E-3. 대본 표시 구조 (프론트엔드)

`/series/[id]` 대본 승인 패널은 **2개 탭**으로 구성:

| 탭 | 데이터 출처 | 표시 방식 |
|---|---|---|
| **씬/컷 구조** (기본) | `v3_scenes` JSON | 씬별 컷 목록, narration/dialogue 구분 표시 |
| **순수 대본** | `v3_chapters.content` (STEP1 텍스트) | 전체 서사 대본 원문 (preformatted) |

**씬/컷 구조 탭 — 컷 표시 규칙**:
- `type=narration`: 흐린 텍스트 + `narr` 태그
- `type=dialogue`: 초록 화자명 배지 + 초록 좌측 보더 + 밝은 텍스트
- `type=mixed`: 노랑 `혼합` 태그

1. `render_service.py`가 `render_type = "ai_video"` 컷 감지
2. 해당 컷의 `image_prompt`, `text`, `scene_meta`를 사용자에게 제공
3. 사용자가 외부 도구로 MP4 제작 → 수동 업로드
4. 업로드된 MP4를 R2에 저장, `clip_url` 갱신 후 파이프라인 재개

**미래 ComfyUI Cloud 연동 (구현 예정)**:
- ComfyUI 워크플로우 JSON + `scene_hint` + `image_prompt` → 고품질 영상 자동 생성
- `render_service.py`의 `ai_video` 분기에서 ComfyUI API 호출로 교체
- 데이터 구조(`render_type`, `scene_meta`, `image_prompt`)는 이미 준비 완료
