## 1. 핵심 철학

> "트랜드한 팩트를 두 인물의 고통으로 보여주는 재미있는 소설"

- **목표**: 실제 트랜드 이슈를 배경으로, 두 등장인물이 겪는 현실적 고통과 고군분투를 팩트와 엮어 흥미롭게 서술하는 시리즈 소설
- **설계 원칙**:
  - **단일 경로** — 폴백 체인 없음. 한 가지 방법으로 완전하게
  - **역할 분리** — NLM(팩트) / Gemini(창작) / ComfyUI(시각) / Remotion(조립) 각자의 역할만
  - **데이터 중심** — 각 단계 결과를 JSON으로 저장, 재시도 시 앞 단계 재실행 불필요
  - **사람이 결정** — 자동 생성은 초안, 최종 확정은 사람

### 역할 구분
| 도구 | 역할 |
|------|------|
| **Gemini 2.5 Pro** | 창작자 — 시놉시스/세계관/대본 생성 |
| **Gemini 2.5 Flash** | 빠른 작업 — 세계관 확장, 요약 추출 |
| **NLM (NotebookLM)** | 팩트 제공자 — 챕터별 팩트/수치 쿼리 |
| **ComfyUI + Fal.ai** | 시각 생성자 — 씬 이미지/영상 |
| **edge-tts** | 음성 생성자 — TTS + 자막 |
| **Remotion** | 조립자 — 이미지+음성+자막 → MP4 |
| **FFmpeg** | 합치기 — 챕터 MP4 concat |
| **사람** | 방향 결정 — 옵션 선택, 대본 수정, 최종 확정 |

> **순서 변경 이유** (2026-04-09 확정):
> 기존에는 시놉시스→세계관 생성 후 감정선을 수정하는 구조여서 **역전**이 발생했음.
> 감정선(두 인물의 관계)이 먼저 확정되어야 그 관계에서 시놉시스가 자연스럽게 흘러나오는 올바른 순서로 변경.

> **세계관 확정 페이지 역할** (2026-04-09 확정):
> - 트랜드 페이지에서 시놉시스 카드 선택 → expand-world API 결과를 세계관 페이지로 전달
> - 세계관 페이지에서 선택된 시놉시스 원본을 읽기전용으로 표시
> - AI가 생성한 모든 필드(캐릭터·장르·갈등·감정선 등)를 사용자가 검토·수정 가능
> - "대본 만들기로 →" 클릭 시 wiki/init 호출 + series_world 확정 → /series/script 이동

> **캐릭터 감정선(/series/characters-emoline) 저장 정책** (2026-04-09 확정):
> - 시리즈 ID와 **무관하게** IndexedDB에 영구 저장 (고정 키: `character_edges` 스토어 / `'edges'` 키)
> - 새 시리즈를 시작하거나 series_id가 바뀌어도 **사용자가 직접 수정하기 전까지 이전 감정선 유지**
> - 감정선은 "캐릭터 풀 전체의 관계 설정"이므로 시리즈별 초기화 없음
> - 단, 사용자가 edge를 추가/삭제/수정하면 즉시 IDB 덮어쓰기 (series_id 발급 여부 무관)
> - 완료 버튼 → `/series/trend` 로 이동 (시놉시스 생성 단계로 진입)

**워크플로우 (확정, 2026-04-09):**
```
캐릭터 설정 → 감정선 설정 → 트랜드·시놉시스 → 시놉시스 카드 선택 → [세계관 확정] → 대본 만들기
(캐릭터 풀)   (관계 사전확정)  (키워드+시놉시스    (expand-world API    (AI결과 검토/수정   (챕터별 생성)
               ↓IDB 저장       생성, 감정선 주입)   자동 실행)           → wiki/init → 확정)
```

**데이터 흐름 (시놉시스 → 세계관):**
- trend/page: 시놉시스 선택 → expand-world → `series_synopsis_selected` (읽기전용), `series_world_draft` (form 형식), `series_trend_context` (wiki 컨텍스트) → `/series/world`
- world/page: 마운트 시 draft 복원 → 시놉시스 카드 읽기전용 표시 → 사용자 수정 → handleProceed → wiki/init + series_world 확정 → `/series/script`

**감정선 → 시놉시스/세계관 주입 방식:**
- `generate-synopsis` API: `emoline_edges` 파라미터로 전달 → 프롬프트에 "사전 확정된 인물 관계" 블록 주입
- `expand-world` API: `emoline_edges` 파라미터로 전달 → `emotionLines[].type` 고정, `arc`만 Gemini 생성
- trend 페이지에서 `loadEmolineEdges()` 로 IDB 읽어 자동 주입 (emoline 설정 없으면 빈 배열 → Gemini 자유 결정)

> **감정선 없이도 동작**: emoline_edges가 비어있으면 기존과 동일하게 Gemini가 자유롭게 관계 설정.

## 5. 전체 파이프라인 흐름

```
[STEP 0] 트랜드 수집 (현재: 아이디어 수집 수준)
  입력: 없음
  출력: 트랜드 키워드 카드 목록
  현재 소스: YouTube API, Naver DataLab (고정 쿼리 — 개선 예정)
  목표 소스: Google Trends RSS + YouTube 24h급상승 + 뉴스 RSS → Gemini 교차분석

[STEP 0.5] 캐릭터 A/B 사전 선택 (optional) ✅
  위치: 트랜드 찾기 > 시놉시스 탭 최상단
  입력: 없음 (캐릭터 풀 목록 표시)
  출력: selCharA, selCharB (id), charACoreDetail, charBCoreDetail (shadow/fear)
  선택 시: shadow 미리보기 표시
  미선택 시: STEP 1에서 Gemini가 자유 선택

[STEP 1] 시놉시스 생성 ✅
  입력: 트랜드 키워드 1개 + [선택된 캐릭터 A/B shadow·fear 프로필]
  출력: 시놉시스 카드 3개 (제목·로그라인·주인공요약·갈등·장르·톤)
  핵심 공식: 팩트(사회이슈) × 막장(불륜·배신·이혼·오피스로맨스) = 시리즈
  캐릭터 프로필 주입 시: 시놉시스가 캐릭터의 shadow·fear에서 흘러나오도록 프롬프트 유도
  API: POST /api/v1/series/generate-synopsis
       body: { keyword, charA_profile?, charB_profile?, api_key }

[STEP 1.5] 세계관 자동 확장 + 세계관 확정 페이지 ✅
  입력: 시놉시스 카드 1개 + [사전 선택 charA/B id] + [emoline_edges]
  출력: world.json (20개 이상 필드) → series_world_draft (form 형식) → 세계관 페이지 표시
  캐릭터풀: _index.json(22명)에서 성별·나이·직업 매칭 → {id}.json 심층 필드 자동 로드
  charA/B 사전 선택 시: Gemini 선택 생략 + 후처리에서 ID 강제 적용
  후처리: Gemini 재작성 방지 — 개별 파일 원본값(shadow/fear 등 8개 필드)으로 덮어쓰기
  emoline_edges 주입: emotionLines[].type 고정, arc만 Gemini 생성
  API: POST /api/v1/series/expand-world
       body: { synopsis, keyword, pre_selected_charA?, pre_selected_charB?, emoline_edges?, api_key }
  
  세계관 확정 페이지 (/series/world):
    - expand-world 결과를 form 형식으로 변환 → 사용자 검토/수정 가능
    - 선택된 시놉시스 원본 읽기전용 표시 (시놉시스 카드 상단 고정)
    - "대본 만들기로 →" 클릭 → wiki/init 호출 + series_world 확정

[STEP 2] 대본 생성 ✅
  입력: world.json + 챕터번호 + 챕터역할 + [직전 챕터 마지막 500자]
  출력: 챕터 대본 (2,500~4,000자)
  저장: IndexedDB linkdrop_series / scripts (seriesId 기반 키)
  API: POST /api/v1/series/generate-script (SSE 스트리밍)
       body: { world, chapter, chapterRole, prev_chapter_ending?, api_key }

[STEP 3] 씬 분해 + 서브씬 세분화 ✅ (클라이언트 처리)
  입력: 챕터 대본 (SSE 완료 시 자동 실행)
  출력: SceneParsed[] → IDB scenes 스토어 + 씬 구성 시나리오.json 다운로드
  처리 위치: 브라우저 (API 호출 없음 — AI 추가 호출 0건)

  1단계 씬 분리 (parseScenes):
    - Gemini가 대본 생성 시 삽입한 `---` 구분자로 5~8개 씬 분리
    - `[HOOK]` 태그 감지 → 해당 씬을 S1(첫 번째)으로 승격
      ★ HOOK 씬은 원래 위치에도 유지됨 (splice가 아닌 copy)
        예: S3이 HOOK → 출력 순서: S3(HOOK) S1 S2 S3 S4 S5 S6
    - `[IMAGE: 한 줄 묘사]` 태그 감지 → 씬의 imageHint 추출 (1차 이미지 힌트)
    - `[IMAGE_N: 묘사]` 태그 감지 → 서브씬별 이미지 힌트 추출 시도
    - 씬 타입 분류: 대화(큰따옴표 6개 이상) / 나레이션(0개) / 혼합
    - [HOOK], [IMAGE: ...], [IMAGE_N: ...] 태그는 씬 파싱 후 대본 텍스트에서 제거 (stripMetaTags)
      → textarea, txt 다운로드, IDB 저장 모두 순수 대본만 저장
      → 태그 정보는 SceneParsed.imageHint / .isHook 필드에만 보존

  2단계 서브씬 세분화 (splitToSubScenes):
    - 각 씬 텍스트를 문장 경계 기준으로 세분화 (TARGET 45자 / 공백 제외 ≈ 10초)
    - **마스터코드 생성**:
        p2(n) = String(n).padStart(2, '0')  — 2자리 zero-pad 헬퍼
        sceneCode (씬 레벨) = `ch${p2(chapter)}s${p2(origIdx+1)}${isHook ? 'h' : 'n'}`
          예: ch01s03h  (챕터1, 3번째 씬, HOOK)
        cutCode (컷 레벨)  = `${sceneCode}c${p2(i+1)}`
          예: ch01s03hc02  (챕터1, 3번째 씬 HOOK, 2번째 컷)
    - 분할 규칙:
        TARGET_CHARS = 45  (목표 글자수 ≈ 10초)
        MIN_CHARS    = 20  (최소 글자수 ≈ 4초)
        MAX_CHARS    = 72  (최대 글자수 ≈ 16초)
        SUB_LIMIT    = 15  (씬당 안전 상한 — 정상 경로에서는 /// 기반으로 자연스럽게 결정됨)
    - **분할 모드 (우선순위 순)**:
        ① `///` 컷 구분자 기반 (최우선 — 의미 단위 보장):
           Gemini가 본문 안 공간·시간·화자·행동·시점 전환 지점에 `///` 단독 줄 삽입
           → `///` split → c01~cNN 생성 (컷 수 = Gemini 판단, 자의적 상한 없음)
           → [IMAGE_N:]과 1:1 정합성 검증 (수 불일치 시 경고 로그)
        ② IMAGE 태그 수 기반 균등 분배 (폴백 1 — 구버전 대본 호환):
           `///` 없는 구버전 대본 → subImageHints.length 그룹으로 균등 분배
        ③ 글자수 기반 (폴백 2 — IMAGE도 없을 때):
           큰따옴표 대화 전환점 → TARGET 도달 → MAX_CHARS 강제
           → SUB_LIMIT(=15, 안전 상한) 초과 시 가장 짧은 인접 그룹 병합
    - imageHint: subImageHints[i] > imageHint(씬 레벨 폴백) 우선순위로 할당 (옵션A)
    - splitReason 기록: 'sentence' | 'dialogue_turn' | 'forced'

  2.5단계 서브씬 이미지 힌트 보완 (별도 API 호출 — payload.done 직후):
    - **전체 컷** 수집 → POST /api/v1/series/sub-image-hints 배치 호출
      (이전: imageHint 없는 컷만 → 현재: 모든 컷 대상 — 1차 힌트를 기반으로 세부묘사 추가)
    - 모델: gemini-2.0-flash (빠른 배치 처리, temperature 0.5)
    - Gemini 역할: 1차 imageHint(공간·분위기)를 기반으로 추가 세부묘사만 생성
      → 표정·시선·자세·소품·조명 변화 등 미시적 디테일 30자 이내
    - 최종 imageHint 합산:
        서브씬 imageHint = 씬 1차 imageHint + ", " + 2차 세부묘사
    - 실패 시 빈 results 반환 → 서브씬 imageHint 없는 상태 유지 (파이프라인 중단 없음)
    - API 완료 후 setScenes + IDB 재저장 (기존 씬 구조 유지, imageHint 필드만 갱신)

[STEP 3.5] 시리즈 ID 확정 ✅ (2026-04-09 결정)
  타이밍: ch01 대본 파싱(parseScenes) 완료 직후
  형식: YYYYMMDD_HHMMSS_ch01s01n
    - YYYYMMDD_HHMMSS : ch01 payload.done 수신 시각
    - ch01s01n        : parsed[0].sceneCode (첫 번째 씬의 마스터코드)
    - 예: 20260409_143022_ch01s01n  /  20260409_143022_ch01s01h (HOOK 씬이 첫 번째인 경우)

  발급 전 임시 ID (tempSeriesId):
    - trend 페이지 키워드 선택 시 생성 (wiki/facts.md 사전 준비 목적)
    - 형식: {키워드슬러그}_{연도}  예: 직장내불륜_2026
    - world.seriesId = world.tempSeriesId = tempSeriesId  (임시 표기)
    - wiki 폴더: wiki/{tempSeriesId}/ → ch01 완료 후 wiki/{realSeriesId}/ 로 rename

  발급 프로세스 (script/page.tsx):
    1. ch01 payload.done 수신
    2. parseScenes(finalContent, 1) → parsed[] 생성
    3. newSeriesId = `${datetime}_${parsed[0].sceneCode}`
    4. POST /api/v1/wiki/rename  { old_id: tempSeriesId, new_id: newSeriesId }
    5. sessionStorage + localStorage의 world.seriesId 업데이트
    6. setWorld({ ...world, seriesId: newSeriesId })
    7. IDB 저장 시 newSeriesId 키 사용 (tempSeriesId 키로는 절대 IDB 저장 안 함)

  저장소 전략:
    발급 전 (ch01 스트리밍 중):
      - 대본 텍스트  → sessionStorage  ld_series_draft_ch01_content  (debounce 1초)
      - NLM 팩트    → sessionStorage  ld_series_draft_ch01_nlm_fact  (즉시)
      - world       → sessionStorage  series_world  (기존)
    발급 후 (ch01 done 이후):
      - 모든 데이터  → IndexedDB  linkdrop_series  (scripts / scenes 스토어)
      - sessionStorage 드래프트 키 삭제 (clearDraftFromSession)
    복원:
      - 페이지 로드 시 IDB 비어있으면 sessionStorage 드래프트 자동 복원
      - ch02~N은 series_id 이미 확정 → 직접 IDB 저장

[STEP 4] 이미지/영상 생성 ⬜
  담당: Fal.ai + ComfyUI (미구현)

[STEP 5] TTS 음성 생성 ⬜
```

### 6-2. 7비트 서사 구조

| 비트 | 역할 | 최소 분량 |
|------|------|----------|
| 비트1 | 여는 이미지 — 공간·감각 디테일 | 3문단 |
| 비트2 | 일상의 균열 — 이상 신호 1개 | 3문단 |
| 비트3 | 첫 대화 — 대사 3회전 이상 | 3문단 |
| 비트4 | 긴장 상승 — 대사 5회전, 거짓말·회피 포함 | 4문단 |
| 비트5 | 비밀의 징후 — 단서 2개 매립 | 2문단 |
| 비트6 | 반전 또는 발견 — 독자만 눈치채는 구조 | 2문단 |
| 비트7 | 닫는 훅 — 다음 챕터를 기다리게 하는 마지막 문장 | 1문장 |

### 6-3. 도입부(챕터1) 특수 규칙

- **임무**: 감정적 위기 1개에 집중 — 전모·원인·연결고리 설명 금지
- **비트2**: 주인공 A 1인에게만 집중 (챕터1에서 두 주인공 동시 등장 금지)
- **비트5**: 주인공 B의 존재를 마지막에 단 1문장으로만 암시 (이름·직업·상황 설명 없이)
- **비트7**: 질문형 훅 — "이게 뭐지?" 하고 다음 화를 누르게

### 6-4. 컨텍스트 주입 레이어

```
세계관 (world.json)
  ├── 캐릭터 Want / Need / coreWound / EmotionArc
  ├── 캐릭터 심층 필드 (개별 JSON 파일 → 자동 주입)
  │     public_face  — 남들에게 보이는 겉모습
  │     shadow       — 절대 들키고 싶지 않은 속모습 (핵심 갈등 엔진)
  │     lie_to_self  — 겉/속 간격을 유지하는 자기기만
  │     fear         — shadow 노출 시 일어나는 일
  │     under_stress — 극한 상황에서 shadow가 새어나오는 방식
  ├── storyBeats[6] — 6챕터 사건 계획 (expand-world 시 생성)
  │     챕터N 생성 시: 이전 beats[0~N-2] + 이번 beats[N-1] 주입
  │     감정선이 바뀌는 챕터에만 "→ 감정선 변화:" 마커 포함
  ├── 감정선 (emotionLines) — 사건과 별개로 작동하는 인물 간 관계 레이어
  │     초기 type + arc(챕터별 변화 스냅샷)로 구성
  │     챕터N 생성 시: arc에서 N 이하 가장 최근 상태 탐색해서 주입
  │     이번 챕터에서 막 바뀐 경우: "※이번 챕터 변화: 이전→현재" 명시
  ├── NLM 팩트 — 나레이션 1~2문장으로만 녹임 (대사 직접 인용 금지)
  └── prev_chapter_ending — 직전 챕터 마지막 500자 직접 주입 (챕터2 이상)
        챕터N 생성 시 contents[N-1].slice(-500)을 "직전 챕터 마지막 장면" 섹션으로 주입
        목적: 실제 쓰인 복선·고유명사·설정이 다음 챕터에 그대로 이어지도록 보장
        챕터1은 prev_chapter_ending 없음 → 해당 섹션 생략
```

### 6-4-1. 사건(事件)과 감정선의 관계

> 사건과 감정선은 별개로 작동하되, 특정 사건이 감정선의 변화를 유발할 수 있다.

```
감정선 (레이어 1) — 인물 간 관계의 현재 상태. 챕터 간 연속성을 갖는다.
  초기: 박준혁 → 김나은: 호기심
  챕터3 이후: 박준혁 → 김나은: 설렘      ← 사건으로 유발된 변화
  챕터4 이후: 박준혁 → 김나은: 죄책감·집착

사건 (레이어 2) — 챕터 안에서 일어나는 일. 감정선 변화의 트리거가 될 수 있다.
  챕터3 storyBeat: "둘이 단둘이 저녁을 먹음 → 감정선 변화: 호기심→설렘"
  챕터4 storyBeat: "선을 넘음 → 감정선 변화: 설렘→죄책감·집착"
```

**emotionLines 데이터 구조:**
```json

  "fromId": "park_jh",
  "toId":   "kim_ej",
  "type":   "호기심",
  "color":  "#9333ea",

    "1": "호기심 — 전세 사기 모임에서 처음 만남",
    "3": "설렘 — 둘만의 저녁",
    "4": "죄책감·집착 — 선을 넘음",
    "5": "공포 — 아내가 눈치채기 시작",
    "6": "파국 — 모든 것이 드러남"
  }
}
```

**챕터N 프롬프트 주입 예시 (챕터4):**
```
- 감정선: 박준혁 → 김나은: 죄책감·집착  ※이번 챕터 변화: 설렘 → 죄책감·집착
- 감정선: 이수진 → 박준혁: 불안 — 이상한 낌새
```

### SceneParsed 인터페이스
```typescript
interface SubScene {
  subIndex: number;
  cutCode: string;      // 마스터코드 (컷 레벨) — ch##s##[h|n]c## (예: ch01s03hc02)
  text: string;
  charCount: number;
  estimatedSec: number;
  imageHint: string;    // 최종값 = 1차(씬 imageHint) + ", " + 2차(서브씬 세부묘사)
                        // 우선순위: subImageHints[i] > (i===0 ? 씬 imageHint : '') > ''
  splitReason: 'sentence' | 'dialogue_turn' | 'forced';
}

interface SceneParsed {
  index: number;          // 표시 순서 (hook이면 0)
  originalIndex: number;  // 대본 원래 순서
  sceneCode: string;      // 마스터코드 (씬 레벨) — ch##s##[h|n] (예: ch01s03h)
  text: string;
  imageHint: string;      // [IMAGE: ...] 추출값 (1차 이미지 힌트)
  isHook: boolean;        // [HOOK] 마킹 여부
  type: 'narration' | 'dialogue' | 'mixed';
  charCount: number;
  estimatedSec: number;
  imageUrl: string;
  status: 'pending' | 'generating' | 'done' | 'error';
  subScenes: SubScene[];  // 2단계 세분화 결과
}
```

**마스터코드 포맷:**
```
씬 레벨:  ch##s##[h|n]       — 8자 고정
컷 레벨:  ch##s##[h|n]c##    — 11자 고정

ch## — 챕터 번호 2자리 (ch01~ch12)
s##  — 씬 번호 2자리 (s01~s08, 대본 원래 순서 기준)
h|n  — HOOK 씬(h) / 일반 씬(n) 구분
c##  — 컷 번호 2자리 (c01~c06)

예: ch02s04nc03
    → 챕터2, 4번째 씬(일반), 3번째 컷
```

**핵심 설계 원칙 — 의상 분리:**
- `fal_identity_prompt`: **얼굴 + 헤어 + 체형만** (모든 시나리오에서 불변하는 외형 정체성)
- `wardrobe.{context}.wardrobe_prompt`: **의상만** (씬 맥락에 따라 교체 가능)
- Fal 이미지 생성 시: `fal_identity_prompt` + `wardrobe[sceneContext].wardrobe_prompt` + `imageHintEn` 조합
- `sceneContext`: `"default"` | `"casual"` | `"stressed"` — 씬 감정/상황에 따라 PromptBuilder가 선택
- 새 의상 추가 = `wardrobe` 객체에 key 추가만으로 확장 (코드 수정 불필요)

**기본 화풍: 실사풍 (real) — `"is_default": true`**
> 모든 씬 이미지 생성의 기본값은 실사풍. 마사코 스타일은 명시적으로 선택할 때만 사용.

**반미화(反美化) 원칙 — 모든 real 파일 적용:**
> AI는 기본적으로 피사체를 미화하는 방향으로 렌더링하므로 아래 지시를 명시해야 현실감 있는 이미지 생성 가능
> - `style_prompt`에 "ordinary Korean [man/woman] you would see on the street, no beauty filter, no skin retouching, realistic natural imperfections, street-cast everyday appearance" 명시
> - `negative_prompt`에 "beauty filter, airbrushed skin, perfect complexion, smooth flawless skin, model look, idol look, celebrity appearance, skin retouching" 명시

**AI 나이 보정 원칙 (한국인 실사화 기준):**
> AI는 동양인을 실제보다 젊게 렌더링하므로 `fal_identity_prompt`에 보정 나이를 요구해야 현실감 있는 이미지 생성 가능
> - 20~30대 → 실제 나이 +5세 요구
> - 40~60대 → 실제 나이 +10세 요구
> - 70대 이상 → 실제 나이 +15세 요구

**기타:**
- `reference_url` 초기값 `""` → text-to-image 모드 (레퍼런스 미확정)
- `reference_url` 채워지면 → IP-Adapter / PuLID 모드 (얼굴 일관성 고정)
- 사용자가 JSON 직접 편집해 프롬프트 튜닝 가능

- **단계별 저장** — 각 단계 결과물 독립 저장, 앞 단계 재실행 불필요
- **씬별 재시도** — 이미지 생성 실패 시 해당 씬만 재생성
- **수동 오버라이드** — 어느 단계든 결과물 직접 교체 가능

 1. 서사 구조의 정교함 (Narrative Architecture)
   * 7단계 비트(Bit) 전략: 단순히 "대본을 써라"는 지시가 아니라, [여는 이미지] → [일상의 균열] → [첫 대화] → [긴장 상승] 
     → [비밀의 징후] → [반전/발견] → [닫는 훅]으로 이어지는 서사 공식을 프롬프트에 강제 삽입했습니다. 이는 AI가 일관된   
     호흡과 긴장감을 유지하게 만드는 강력한 장치입니다.
   * 역할별 특화 가이드: 도입부, 전개, 클라이맥스, 결말 등 챕터의 역할에 따라 AI의 작법 지침을 동적으로 변경합니다. (예: 
     도입부에서는 사건 전모를 숨기고 감정적 위기에만 집중하도록 지시)

  2. 인물 및 심리 엔진 (Character & Emotion Engine)
   * Want/Need 축 기반 설계: 로버트 맥키의 시나리오 작법론을 적용하여, 캐릭터의 표면적 욕망(Want)과 내면적 결핍(Need)을  
     구분해 AI에게 주입합니다.
   * 감정선(Emotion Arc) 추적: 챕터별로 변화하는 인물 간의 관계와 감정 상태를 상태 머신처럼 관리하며, 이번 챕터에서      
     일어날 심리 변화(prev_state → current_state)를 명시적으로 전달합니다. 이는 캐릭터 붕괴(OOC)를 방지하는 핵심
     로직입니다.
   * 심리적 투영(Core Wound): 두 인물이 공유하는 근원적 상처(Core Wound)를 서사 엔진으로 활용하여, 대화와 행동의 개연성을
     확보합니다.

  3. 지식 주입 및 맥락 유지 (Knowledge & Context Management)
   * NLM 팩트 주입 (RAG): 외부 지식 베이스(NLM)에서 실시간으로 팩트를 쿼리하여 대본에 녹여냅니다. 이는 AI의
     할루시네이션(가짜 정보)을 줄이고 전문적인 디테일을 더하는 역할을 합니다.
   * 상태 전이(State Carryover): 이전 챕터의 마지막 장면(prev_chapter_ending)을 다음 챕터의 입력으로 넣어, 챕터 간의     
     연결성을 물리적으로 보장합니다.

  4. 출력 제어 및 메타데이터 (Output Control)
   * 멀티모달 대비 로직: 대본 중간에 [IMAGE: 시각 묘사]와 [HOOK] 태그를 자동 삽입하도록 설계되어 있습니다. 이는 향후 영상
     제작이나 썸네일 생성, 하이라이트 추출을 위한 데이터 구조화를 미리 고려한 것입니다.
   * 문체 헌장(Style Charter): "감정 단어 사용 금지", "신체적 반응으로 묘사", "문장 리듬(종결어미 중복 금지)" 등 극도로  
     구체적인 문체 규칙을 시스템 인스트럭션으로 부여하여 생성물의 문학적 품질을 강제합니다.

  5. 종합 평가
   * 강점: 웹소설/드라마 작법의 핵심 원리(비트, 훅, 내면 결핍 등)를 코드와 프롬프트 수준에서 완벽하게 체계화했습니다.    
     단순한 '글쓰기 도우미'가 아니라 '서사 구조 설계자'에 가까운 로직입니다.
   * 한계 및 고려사항: 로직이 매우 정교한 만큼 AI 모델(Gemini 2.5 Flash 등)의 인스트럭션 준수 능력에 크게 의존합니다.    
     프롬프트가 매우 길기 때문에(Long Context), 모델이 뒤쪽의 세부 규칙을 간과할 위험이 있으나, 이를 비트 단위 분량      
     제한으로 보완하고 있습니다.
