# Book Feedback Reader — 독자 페르소나 피드백 스킬 (v2)

책 원고를 타깃 독자 관점에서 시뮬레이션 검증하는 스킬. 편집자·전문가 관점이 아닌 **실제 독자가 이 책을 어떻게 읽을지**에 집중한다.

v2 변경점: 실용서/서사형 모드 분리, Harness Engineering(Generator↔Evaluator) 적용, 분량 가드레일, 관찰형 서술 강제, 경험 주입 검증 항목 추가.

## 이 스킬을 쓰는 이유

집필자는 자기 원고에 익숙하다. "이 정도면 이해되겠지" 같은 내부자 편향이 생긴다. 이 스킬은 페르소나를 세워 각자의 배경 지식과 동기에서 원고를 다시 읽게 한다. 그 결과 막힘·이탈 지점이 드러난다.

## 적용 시점

- 집필 중간(2~3챕터 완성 후): 방향 점검
- 탈고 직후, book-editing 전: 구조적 문제 발견
- 베타리더 모집 전: 사전 시뮬레이션

## Phase 1 — 입력 정리

다음 정보가 없으면 추측하지 않고 질문한다.

```
## 원고 정보
- 제목·가제:
- 장르·카테고리:
- 콘셉트 한 줄:
- 분량:
- 피드백 범위: (예: Ch 1~3 또는 전체)

## 타깃 독자 정보
- 연령대:
- 직업·역할:
- 사전 지식 수준: (초심자/중급/전문가)
- 구매 동기:
- 읽기 맥락:

## 기획 정보 (실용서일 때 추가)
- 독자가 책을 덮은 후 할 수 있어야 하는 것: (작업·결과물 명시)
- 전제 도구·환경: (있다면)
- 경험·사례 주입 의도: (book-writing-pro 사용 시)
```

## Phase 2 — 모드 선택

원고 성격에 따라 검증 항목이 다르다. 사용자가 명시하지 않으면 장르·콘셉트로 자동 판정하고 사용자에게 확인받는다.

### 실용서 모드 (Practical Mode)

대상: 가이드북, 기술서, 자기계발서, 매뉴얼, 워크북, 현장 노트형 실용서, 스킬북

검증 5축:
1. **재현 가능성** — 독자가 이 챕터를 따라 했을 때 같은 결과에 도달할 수 있는가
2. **전제 명시성** — 사전 지식·도구·환경 가정이 드러나 있는가, 숨겨진 전제가 있는가
3. **실습 연결성** — 이론·설명과 예제·실습이 정합적인가, 따로 노는 부분이 있는가
4. **참조 충분성** — 이 챕터만 읽고 이해할 수 있는가, 외부 자료 없이도 가능한가
5. **경험 주입 검증** — (book-writing-pro 사용 시) 1인칭 경험·현장 사례가 약속된 비중으로 들어있는가, 추상 설명만 있는가

### 서사형 모드 (Narrative Mode)

대상: 에세이, 산문, 소설, 회고록, 인문 교양서, 현장 기록 중 서사 비중이 높은 책

검증 5축:
1. **이해도** — 따라올 수 있는가
2. **몰입도** — 다음 페이지로 넘기고 싶은가
3. **지루 구간** — 읽기 속도가 떨어지는 구체적 위치
4. **의문점** — 페르소나가 묻고 싶어지는 지점
5. **이탈 위험** — 책을 덮을 가능성이 있는 구간

### 혼합 모드

실용서이면서 1인칭 서사 비중이 높은 책(예: 〈AI와 함께 일하는 법〉 같은 현장 노트형)은 두 모드를 함께 적용한다. 사용자에게 확인받고 진행한다.

## Phase 3 — 페르소나 설계

타깃 독자 정보를 바탕으로 **3~5명의 페르소나**를 구성한다.

### 구성 원칙

- **최소 3명, 최대 5명**
- **스펙트럼 차이 필수**: 지식 수준·동기·읽기 강도 중 최소 2개 축에서 서로 다르게
- **이름·직업·한 줄 상황**까지 구체화
- **금지**: 추상적 페르소나("초심자 A"), 비슷비슷한 페르소나, 집필자 본인과 닮은 페르소나만 만드는 것

### 페르소나 카드 템플릿

```
## 페르소나 N: [이름]
- 나이·직업:
- 사전 지식: (구체적으로 — "Claude는 써봤지만 스킬은 처음" 같이)
- 왜 이 책을 샀는가:
- 어떤 상황에서 읽는가:
- 기대하는 것:
- 참을 수 없는 것:
- 핵심 질문: (이 페르소나가 책에 던지는 1~2개 질문)
```

페르소나 카드를 사용자에게 먼저 제시하고 확인받는다. 수정 요청이 있으면 반영 후 Phase 4로 진행한다.

---

## Phase 4 — Generator: 챕터별 관찰 시뮬레이션

이 단계는 **관찰만** 한다. 평가·점수·우선순위 판정은 하지 않는다. 평가는 Phase 5(Evaluator)의 몫이다.

### 관찰형 서술 강제 규칙 (가장 중요)

페르소나 반응을 쓸 때 다음 규칙을 지킨다.

- **금지 표현**: "~할 것이다", "~할 수 있다", "흥미로울 것이다", "지루해할 것이다" 같은 추측형
- **권장 표현**: "이 페르소나의 사전 지식 기준에서 X 용어는 설명 없이 등장한다", "3번째 문단의 Y는 1장에서 정의되지 않은 채 사용된다", "예제 코드와 본문 설명의 변수명이 일치하지 않는다" 같은 **관찰 가능한 사실**

이 규칙의 이유: 추측형 서술은 집필자에게 가치가 없다. "이 독자가 지루해할 것이다"라는 문장으로는 무엇도 고칠 수 없다. "X 위치에서 Y라는 사전 지식이 가정되고 있는데 페르소나는 그 지식이 없다"는 문장이라야 수정이 가능하다.

### 실용서 모드 출력 형식

```
## Ch [번호] [챕터 제목]

### 페르소나 1 [이름]
- 재현 가능성 관찰:
  - [위치]: [관찰된 사실]
- 전제 명시성 관찰:
  - [위치]: [숨겨진 전제 또는 명시된 전제]
- 실습 연결성 관찰:
  - [위치]: [이론과 실습의 정합/불일치]
- 참조 충분성 관찰:
  - [위치]: [외부 참조 없이 이해 가능한지]
- 경험 주입 관찰: (book-writing-pro 사용 시)
  - [위치]: [경험 사례의 유무·구체성]

### 페르소나 2 [이름]
(동일 구조)
```

### 서사형 모드 출력 형식

```
## Ch [번호] [챕터 제목]

### 페르소나 1 [이름]
- 이해 막힘 위치:
  - [구체적 위치]: [이 페르소나의 사전 지식 기준에서 어떤 부분이 미설명인지]
- 읽기 속도 저하 위치:
  - [구체적 위치]: [관찰된 원인 — 반복/긴 문단/추상 설명 등]
- 의문이 발생하는 위치:
  - [위치]: [어떤 질문이 떠오르는지]
- 이탈 가능 위치:
  - [위치]: [관찰된 이유]

### 페르소나 2 [이름]
(동일 구조)
```

### 분량 가드레일

- **페르소나 1명 × 1챕터 = 최대 400자**
- **챕터당 페르소나 반응 합계 = 최대 1,500자**
- **전체 Phase 4 출력 = 원고 분량의 30% 이내**
- 이 한도를 넘으면 가장 미미한 관찰부터 잘라낸다

### 페르소나 일관성 점검

- 초심자 페르소나가 전문 용어를 당연히 이해하는 것처럼 쓰지 않는다
- 한 페르소나의 사전 지식 기준이 챕터마다 흔들리지 않는다
- 집필자 본인의 시선이 페르소나에 섞여 들어가지 않는다

## Phase 5 — Evaluator: 패턴 평가

Phase 4의 관찰 데이터를 입력으로 받아 **별도의 평가 작업**을 수행한다. Phase 4와 Phase 5는 출력 단계를 분리한다(Harness Engineering 원칙).

### 평가 항목

```
## 패턴 평가

### 모든 페르소나가 막힌 지점
- [챕터·위치]: [관찰 N건 누적] — [추정 원인]

### 페르소나별로 반응이 갈린 지점
- [챕터·위치]: 
  - 페르소나 A 관찰: [요약]
  - 페르소나 B 관찰: [요약]
  - 갈림 원인: [분석]

### 반복되는 의문점·전제 누락
- [항목]: N명의 페르소나가 동일 위치에서 동일 관찰

### 위험 누적 챕터
- Ch N: 페르소나 N명 중 M명에게서 막힘 또는 이탈 관찰

### (실용서 모드) 재현 가능성·경험 주입 종합
- 재현 가능성이 흔들리는 챕터: [목록 + 근거]
- 경험 주입이 약속 대비 부족한 챕터: [목록 + 근거]
```

### 평가 원칙

- Phase 4의 관찰만 근거로 한다. 새로운 추측을 추가하지 않는다
- "모든 페르소나가 막힘"은 구조 문제(우선순위 높음)
- "갈린 지점"은 타깃 재정의 또는 분기 서술 필요
- "반복 누락"은 본문 보강 또는 FAQ 박스 필요

## Phase 6 — 수정 우선순위 리포트

집필자가 바로 수정에 착수할 수 있는 형태로 정리한다.

```
## 수정 우선순위 리포트

### 🔴 High (즉시 수정)
1. [Ch·위치]: [관찰된 문제] → [권장 조치]
2. ...

### 🟡 Mid (구조 점검 후 수정)
1. [Ch·위치]: [관찰된 문제] → [권장 조치]
2. ...

### 🟢 Low (여유 있을 때)
1. [Ch·위치]: [관찰된 문제] → [권장 조치]
2. ...

### 유지할 강점
- [Ch·위치]: [어떤 페르소나의 어떤 관찰에서 강점이 드러났는지]
```

### 우선순위 판정 기준

**실용서 모드:**
- **High**: 재현 불가, 핵심 전제 누락, 실습-본문 불일치, 경험 주입 약속 위반
- **Mid**: 참조 충분성 부족, 일부 페르소나의 전제 누락, 단일 챕터의 경험 부족
- **Low**: 용어 선택, 사소한 보강

**서사형 모드:**
- **High**: 2명 이상의 페르소나가 이탈 관찰 / 핵심 개념 이해 실패 / 구매 동기 훼손
- **Mid**: 1명 이탈 관찰 / 반복 의문점 / 지루 구간 누적
- **Low**: 개별 취향 차이 / 사소한 용어

강점도 반드시 남긴다.

### 분량 가드레일

- High 항목: 최대 5개
- Mid 항목: 최대 7개
- Low 항목: 최대 5개
- 초과 시 영향 범위가 좁은 항목부터 잘라낸다

## 출력물

대화창 텍스트로 다음 순서대로 제공한다.

1. Phase 1 입력 정리 (확인용)
2. Phase 2 모드 선택 (사용자 확인)
3. Phase 3 페르소나 카드 (사용자 확인)
4. Phase 4 Generator 관찰 시뮬레이션
5. Phase 5 Evaluator 패턴 평가
6. Phase 6 수정 우선순위 리포트

사용자가 ".md로 저장"을 요청하면 Phase 4~6을 하나의 파일로 묶어 저장한다.

파일명 규칙: `BFR_[책제목]_[날짜].md`

## 금지 사항

- **추측형 서술 금지**: "~할 것이다", "~할 수 있다", "흥미로워할 것이다" 같은 표현. Phase 4의 관찰형 규칙 위반
- **집필자 기분 맞추기 금지**: "전반적으로 훌륭합니다" 같은 의례적 총평
- **Phase 4와 Phase 5 섞기 금지**: 관찰 단계에서 평가하지 않는다, 평가 단계에서 새 관찰 만들지 않는다
- **편집자 관점 섞기 금지**: 문장 다듬기·구조 개선 제안은 book-editing의 영역. 콘셉트·시장 진단은 book-feedback-editor의 영역
- **팩트체크 금지**: 사실 여부 판단은 이 스킬의 범위가 아니다
- **페르소나 무너뜨리기 금지**: 중간에 페르소나 설정을 잊고 "객관적 관점"으로 말하지 않는다
- **분량 가드레일 위반 금지**: 한도를 넘으면 미미한 관찰부터 자른다
- **과장·추상 표현 금지**: "매우", "정말", "완벽하게", "혁신적인" 등

## Harness Engineering 적용

이 스킬은 홍작가님 스킬 생태계의 Harness 원칙을 따른다.

- **Generator(Phase 4) ↔ Evaluator(Phase 5) 분리**: 관찰과 평가가 같은 단계에서 섞이면 평가가 관찰을 왜곡한다. 두 단계를 명시적으로 끊는다
- **원본 보존 레벨 L1**: 원고 본문은 절대 수정하지 않는다. 인용·요약만 한다
- **AI 흔적 제거**: 추측형·과장·모호 표현 금지 (위 금지 사항 참조)
- **분량 가드레일**: Phase 4·Phase 6에 명시된 한도 준수

## 다른 스킬과의 관계

- **book-planning**: 기획 단계. 이 스킬은 원고가 있어야 동작한다
- **book-writing / book-writing-pro**: 집필 단계. book-writing-pro의 경험 주입 단계와 직접 연결됨 (실용서 모드 5번째 검증축)
- **book-feedback-editor**: 편집자 관점 피드백. 두 스킬을 병행하면 독자가 막히는 지점과 편집자가 지적하는 지점을 교차 검증할 수 있다
- **book-editing**: 문장·구조 퇴고. 이 스킬의 리포트를 입력으로 받아 실제 수정 작업을 수행한다
- **book-research**: 근거 자료 보강. 이 스킬에서 "전제 누락"·"의문점"으로 반복 제기된 항목을 보강할 때 사용

권장 파이프라인:
`book-writing-pro` → **book-feedback-reader** → (병행) `book-feedback-editor` → `book-editing` → (필요 시) `book-research` 보강 → `book-editing` 재실행
